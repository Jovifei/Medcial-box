## 当前可证实的原因与边界

2026-10-19 21:35–21:39（北京时间）的服务器只读快照：原 `/dev/vda3` ext4 根文件系统总 41,881,894,912 B（39.006 GiB），已用 39,114,280,960 B（36.428 GiB），普通账户可用 831,971,328 B（0.775 GiB），`df` 为 98%。相对 10 月 18 日 18:13，已用增加 210,358,272 B（约 200.61 MiB）；inode 仅用 24%，因此当前瓶颈是块空间。

`/var/lib/docker`、`/var/lib/containerd`、部署目录、数据库卷和私照卷都在这块系统盘；不是独立数据盘。当前 Docker 有 93 个唯一镜像 ID、23 个容器、18 个卷，供多个项目共用。普通维护账户不能遍历 Docker 底层（710/711、root 属主）；其 `du` 显示 4 KiB 是权限造成的误导，**不是 Docker 的实际大小**。只读 `docker system df` 在 12 秒界限内没有返回，因此尚无镜像共享层、构建缓存、容器日志与其它项目的物理占用分摊。不能说“药箱把云盘占满”，也不能指定任何无证据的清理对象。

已能直接测得的占用：药箱原数据库卷 48,820 KiB（47.68 MiB），私照卷 4 KiB；`/var/log` 约 347 MiB、`/var/cache` 约 217 MiB、`/home` 约 65 MiB。这些目录可能包含多项目资源，彼此不与根盘已用量另行相加。药箱原 API/PG 容器仍运行。原 API 镜像报告大小 222,603,478 B，仍有容器引用，必须保留。旧 UI 镜像报告大小 222,647,385 B，当前未见容器引用，但它与原镜像共享基础层，真实可回收小于报告大小；以前的本机归档也未完成，因此不删除。即使按 0.208 GiB 全额上界计算，它也远不足以解决容量。

### 已定位的其他项目实际用量

2026-10-19 晚间对可读目录的 `du -x -B1` 只读聚合，**ETF/基金项目** `/opt/china-fund-decision` 已可见 **10,430,976,000 B（9.715 GiB）**。其中 `backups` **5,186,330,624 B（4.83 GiB）**，其余多份 `release`/`deploy` 目录合计约 5.24 GB（十进制）；这是真实分配块，不是镜像逻辑大小。该次顶层统计因部分目录无权读取以退出码 1 结束，所列是**可见下界**，不能称整个 ETF 项目的完整总量。

备份目录可读聚合有 75 个文件、已分配 5,186,289,664 B；其中 2026 年 9 月修改的 65 个约 4.50 GB，10 月修改的 4 个约 0.683 GB。7 个一级子目录只占约 1.06 GB，根目录直接文件约 4.12 GB。这些是元数据统计，未读取备份内容、凭据或业务记录。`backups` 正作为 bind mount 提供给 ETF 当前运行的 API/worker/scheduler 及两个停机旧容器，**不能直接移动、删除或断开挂载**。需该项目维护者按恢复链、保留期限及引用逐文件审定；经完整加密归档、哈希及恢复验证且确认不再被运行/回滚使用后，才能提出具体候选给 Owner 审批。

ETF 项目源码的只读复核进一步解释了积累方式：其 `scripts/backup_postgres.sh` 每次生成独立的完整 `pg_dump --clean` 压缩 `.sql.gz` 与 `.sha256` 成对文件、原子发布，**没有自动删除保留期**；其测试明确防止按年龄自动清理。`deploy/aliyun/update.sh` 在每次升级前另建备份；项目文档中的“本地30天、OSS私有、定期恢复”只是建议，`.env.production.example` 的 `RETENTION=30` 未被该脚本执行。目录里另有 `.dump` 格式的历史预部署备份，不能按 `.sql.gz` 同一种恢复方式处理。当前维护账户无 crontab，匹配的 systemd timer 未见；root/其他用户定时任务仍未知。这些源码事实支持“备份随部署积累”是 4.83 GiB 的一个直接原因，但不能凭文件年龄推定可删。

**候选判定**：只把旧于30天且非当前/上一发布、非最近迁移的唯一回滚点的单份完整归档纳入文件级审查；`.sql.gz` 必须连同对应 `.sha256` 核验，`.dump` 单列。先在 E 盘受保护接收区做加密完整副本与哈希，再在获准的隔离 PostgreSQL 实际恢复；至少保留另一独立恢复副本及必要密钥。ETF 项目维护者确认运行/回滚依赖、Owner 对精确文件逐项批准后，才能讨论移除服务器原件并用 `df` 验净释放。当前能直接确认的可释放字节数仍 **0 B**；不能把整个 4.83 GiB 计作收益，也不能动挂载目录、数据库卷、当前回滚点、唯一备份、sidecar、`.pending`、其它项目数据。

Docker 的 111 个标签/93 个唯一镜像 ID 中，逐标签显示合计：逐星图片项目 53 标签/39 唯一 ID/约 24.0 GB，ETF 13/13/约 11.14 GB，china-fund 7/6/约 4.38 GB，药箱 2/2/446 MB，JourVolt/MateLink 17/14/547 MB，其余共享或未归类 19/19/约 5.23 GB。**这些数字是各标签显示的逻辑大小合计，跨镜像共享层重复，绝不是磁盘实际占用、也不是可释放量。** `docker ps --size`、单容器 `inspect --size` 和全局 `system df` 均在有界时间内无输出；镜像 history 缺层ID，不能可信求出逐项目独占层。容器日志宿主路径权限拒绝；未通过其它容器的主机挂载绕过权限。第二次 `/opt` 顶层聚合遇 SSH 连接超时，未执行到远端；其余项目实际目录大小仍未知。

模型权重、候选镜像与加密接收区已放本机 E 盘；这改善后续布局，但现有服务器实际释放空间为 **0 B**。不将 48 MiB 在线家庭库迁成本机唯一数据库：家用电脑失联会同时中断家庭、库存、邀请和提醒；当前迁库也不能解决容量。

## 容量测算与只读归因

39 号回执的 5 GiB 新增维护峰值预算及峰值 `df` 不超过 80% 的工程目标，在今日新基线下算出 40 GiB 不扩盘时需先实际、安全释放约 **11.67 GiB**。原60GiB估算仅说明维护预算为何紧张，不能证明某项目占满，也不构成购买建议。维护峰值与最终回收目标均须在实际归因后重新核算；若无法安全释放所需空间就停止升级。

**当前执行：无扩容优化。** 已先找到 ETF 可见下界 9.715 GiB，其中备份 4.83 GiB，但**现在可批准删除量仍为 0 B**；它们属于另一个项目且备份目录正在被挂载。下一步按上面的格式/恢复规则取得精确冷档案候选。无法精确归因的 root 专属目录，需要 Owner 提供原实例上获准的只读特权聚合统计：至少分别给出 `/var/lib/docker`、`/var/lib/containerd`、`/var/log`、`/var/cache`、`/home` 的实际分配块，及其他 `/opt` 项目的目录聚合。建议由可信管理员在 ECS Workbench 内按批准维护窗口执行低优先级、只读的 `du -sx -B1` 统计；不要回传文件内容、凭据或家庭资料。随后逐项给出“保留/可归档/待 Owner 决定”清单；只有本机完整副本、哈希、原项目依赖及回滚路径都核验后，才讨论精确删除。绝不使用 `docker system prune`、删卷、删共享镜像或清系统日志来赌空间。

若 Owner 打开原 ECS 的可信管理员只读会话，拟执行的**精确命令范围**如下；命令只输出目录名与已分配字节，不读取文件内容，不写临时文件，单项超时后停止而非换通路。运行前后都先看 `df`；低优先级的 `du` 在共享主机负载异常时立即终止。

```sh
df -B1 /
timeout 120s nice -n 19 du -x -B1 -d1 /opt 2>/dev/null
timeout 120s nice -n 19 du -x -B1 -d1 /var/lib/docker 2>/dev/null
timeout 60s nice -n 19 du -sx -B1 /var/lib/containerd /var/log /var/cache /home 2>/dev/null
df -B1 /
```

这里不会调用 `sudo` 猜口令或借宿主挂载容器越权；执行前须确认管理员会话确属原实例、命令获准且输出不含私有业务内容。Docker 层/卷的项目归属仍需结合只读 inspect 和引用关系，不把目录字节自动分给某一项目。

## 发布顺序及独立门槛

1. 容量：按其他项目只读归因；如现有权限不足，请 Owner 通过原实例正式只读管理员路径提供聚合结果。逐项审批归档/清理后实测 `df` 与容器健康，达到维护余量才继续；不扩盘。
2. 工具与执行权限：原组合脚本在本机进程启动前返回一次 `blocked by policy`，原因未知，Owner 没有审批弹窗；这不是云端 Docker 拒绝。不得改名、拆分或换执行器重放**该被拒动作**。可向官方支持澄清原事件，但不能由此推定一个经过独立审查、实质不同的新维护方案当前也必然被禁；新方案须在执行前核实当期工具权限和其它真实数据门槛，未核实前不执行生产写操作。
3. 数据：在获准停写窗口对原数据库与私照同点配对备份，校验两份副本并在获准的隔离位置恢复；核对两个原家庭、成员和业务归属。当前 E 盘接收区仅通过合成验密，**未取得真实备份/恢复**；恢复身份另存离线副本。
4. 服务：固定源码、镜像摘要、五份迁移及旧 API 到新家庭接口的契约；在原卷保留和可回退的维护计划下升级。现网仍是旧 API，不能用新客户端直接验收。
5. 客户端：手机现装 1.0.3+6 的历史证书必须与覆盖包兼容。1.0.6+8 的普通 Release 当前未签；新建另一个正式证书不能直接保留原安装数据覆盖。须明确原证书合法续用或支持的签名/草稿迁移路径，再做保数据 `adb install -r`。iPhone 小程序不受 Android 证书限制，但仍受 API/两家保全门槛限制。
6. 真机及发布：实际两家庭首页返回、加入/切换、拍照草稿、扫码候选、保存重开、异常网络与回滚核验全部通过后，才进入正式发布评估；CI 和合成服务测试不算真机 PASS。
