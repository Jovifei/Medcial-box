## 1. 目标与范围

- 改进对象：小药箱 M1–M5（状态准确、找药与识别、不确定信息、记录与纠错、可用性），方向与验收口径见共识表第一轮 D0 条目。
- 主线：以 Codex「先跑通一个家庭的实际操作，再修真实卡点」为主线；准备工作可并行，但实际试用前必须确认测的是哪一版、账号/环境已获准、无已知越权或数据损坏阻断。
- 具体最小改动：不由本文件预定；待映射证据到位后另行立行、再逐项表决。

## 2. 主线 T1–T4

- **T1 版本固定**：先固定两端版本与许可——微信小程序 1.2.1 源码及上传回执、Android build 20 装机证据、测试资格；M1–M5 映射对照表（版本/SHA → 已具备/缺失/未验 + 证据，纳入 PR #14 现状）作为 T1 的一部分出表。未证实的项标「未验」，不虚构缺失。
- **T2 P0 双机双账号验收**：在获准测试环境下，用虚构药品跑通一个家庭的四步验收——邀请、录入与找药、识别失败回退（手填）、导出与撤权；同场顺带核对 M1–M5 实况。T2 真实账号、测试环境和分享对象须先获准，不能只给 T4 写启动门槛。硬门槛：T2 实际开跑前必须确认测的是哪一版、账号/环境已获准、无已知越权或数据损坏阻断。
- **T3 P1 只修最卡前两处**：复盘后 2–3 个工作日内只修最卡的前两处；附自动化回归、双机复测及独立验收。最小改动清单 = T2 结果 + 映射表汇合后由 Muse 组织逐项表决定；实施每项独立提交、中文标题注明 M 条目。
- **T4 P2 五家庭七天试点**：5 个家庭试用 7 天。达标定义：至少 4/5 的家庭在 **5 分钟内独立录完一药一批**，至少 3/5 的家庭主动回来查药，作为下一轮试用规模的决策依据（小样本试点建议，不是安全证明或推广成功结论）。T4 启动前四项须先报业主确认，未确认不开跑：参与人、两个微信账号、测试家庭、1.2.1 体验资格；数据及分享范围同样须确认，不自动招募或扩大。

## 3. 数据与验收口径

- 合成测试与真实设备流程互补，不二选一。合成接口/Widget 测试查失败态、边界字号、重复提交；真实设备流程用获准测试账号 + 虚构药品查邀请、录入找药、撤权、识别失败手填、导出。
- 全程不碰真实药品/家庭数据；「真实」指设备与操作，不等于授权私人健康资料。初轮分享/导出只给获准测试对象。
- M1「保留旧库存」仅限同一授权家庭：切家庭/撤权失效不得继续展示越权缓存。
- 撤权语义：撤权禁止后续读取、修改、导出及越权缓存展示；撤权后复查读取、修改和再次导出，失败或缓存回退时也不得显示已失权的数据；不承诺收回对方此前合法保存的导出/截图。
- M1–M5 验收场景直接复用 P0 四步表，避免两套验收。

## 4. 阻断项

- 越权、错家庭、丢数据、重复写入，任一出现即暂停扩大试用并定位修复复测，不受「前两处」上限限制、不带风险进 T4。
- 「前两处、2–3 工作日」仅适用于一般体验问题的范围/工时估计。
