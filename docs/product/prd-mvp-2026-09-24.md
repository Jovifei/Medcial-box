# 增量 PRD：家庭药箱 MVP（P1 手动录入＋导出 → P2 家庭共享）

- 日期：2026-09-24
- 范围：本轮 MVP = 路线图 P1 + P2 的代码与合成测试；P3（拍照识别）与 P4（上线试用）不在本轮，见文末一句话说明。
- 上游权威：`tasks/plans/2026-09-24-mvp-roadmap.md`、`docs/product/requirements.md`。本 PRD 为增量文档，不推翻任何已定决策。

## 1. 产品目标

解决"家里有什么药、各剩多少、何时过期"三个高频痛点：家庭成员通过手动录入维护共享药品清单与多批次库存（允许数量未知或为零），系统按有效期原文精度提示临期／过期／本月到期；用户可将全量库存一键导出为结构清晰、显式标注不确定状态的 Markdown 文件，交给自己选择的外部 AI 辅助分析，而应用本身不做任何问诊或用药推荐。

## 2. 用户故事

1. 作为首次使用的小程序用户，我登录后只创建了我的账号；在进入药箱前，我手动创建一个家庭并自动成为 owner，这样我的药品数据归属清晰，也为 P2 受邀成员预留了入口。
2. 作为家庭成员，我手动新建一条药品并为每个包装批次分别记录数量、单位与有效期；数量可以填"未知"或确定的"0"，把"盒"换算成"片"之前系统必须让我确认换算数量，避免库存失真。
3. 作为家庭成员，我编辑药品或批次时若与他人并发修改，我提交旧版本会收到 409 冲突提示，先看到最新值再决定是否重新提交，不会被静默覆盖。
4. 作为家庭成员，我在药箱首页看到临期（精确到日的提前 30 天）、过期、本月到期和待补充（数量未知/日期缺失）的区分展示，一眼知道哪些药需要处理。
5. 作为家庭成员，我手填说明书摘要并记录来源，对照包装内说明书后可显式标记"本人已核对"；未核验的内容不会被冒充为已确认资料。
6. 作为家庭成员，我为自己记录实际每日剂量备注，它独立于药品通用说明，默认只有我能看到。
7. 作为家庭成员，我导出 Markdown 时默认不含任何个人剂量备注，预览后可选择包含我有权查看的部分；导出中未知数量、零库存、过期都显式标注；我可以复制文本，也可以写本地 `.md` 后用 `wx.shareFileMessage` 分享。
8. 作为家庭 owner，我生成一次性邀请凭据（72 小时失效），家人先用自己的微信登录再加入；已有家庭关系的用户会被拒绝并提示先处理原家庭，系统不自动合并药品。
9. 作为家庭 owner，我移除某成员后，该成员的会话立即失去全部家庭数据访问权限。
10. 作为家庭成员，我看到他人的剂量备注仅当对方主动选择"全家可见"；导出同样遵守该权限。

## 3. 需求池

### P0（本轮必须，对应 roadmap P1 + P2 全部条款）

**数据与身份**
- 迁移 `002_core_inventory.sql`：用户、家庭、成员、哈希会话、药品、库存批次、个人剂量备注；药品/批次含 `family_id`、创建/修改人、修改时间、整数版本。
- 登录只创建用户；`POST /api/v1/families` 手动建家庭并成为 owner；每账号仅一个家庭。
- `POST /api/v1/auth/wechat`：`wx.login` 临时 code 仅服务端交换 openid；发放随机会话令牌，库中只存哈希与过期时间；AppID/AppSecret 仅服务端环境读取；自动化测试注入假微信网关，无公开"测试登录"接口。

**药品与批次**
- 药品与批次分离；列表/详情/新建/编辑/归档 API，每个读写端点核对家庭成员身份。
- 更新请求携带记录版本，版本不符返回 HTTP 409。
- 批次数量：`null`=未知、`0`=确定耗尽；盒→片/袋换算数必须经用户确认。
- 有效期保存原文与精度（`YYYY-MM-DD`/`YYYY-MM`/未知）：年月仅显示月份，过月才标过期，当月标"本月到期"；精确到日默认提前 30 天临期。

**小程序页面**
- 药箱首页（库存、临期/过期计数、区分显示）、手动录入/编辑、批次详情、导出预览。
- 说明书摘要手填 + 来源 + 核验状态 + 显式"本人已核对"标记。
- 个人剂量备注作为独立成员记录，不从药名或通用说明生成。

**导出**
- `POST /api/v1/exports/markdown`：全量库存分区清单、批次、有效期精度、已确认的说明书摘要及来源；未知/零/过期显式标注；`includePersonalDosage` 默认 `false`，勾选时仅含当前用户有权查看的备注。
- 小程序预览后写本地 `.md` 再 `wx.shareFileMessage`，并始终提供复制文本。

**P2 家庭共享**
- owner 生成一次性邀请凭据，服务端只存哈希，72 小时失效；被邀请人先自行登录再加入；已有家庭者拒绝并提示，不自动搬移/合并药品。
- 每次读写按服务端会话查成员关系；owner 移除成员后立即失效。
- 剂量备注默认仅本人可见，可选"全家可见"；导出遵守相同权限。
- 并发编辑 409 流程：查看最新值后重新提交，不静默覆盖。

**验收**
- 真实 PostgreSQL 验证迁移与增删改查（环境可用时）。
- 合成测试覆盖：无家庭会话、跨家庭拒绝、过期算法、同药多批次、未知与零、409 冲突、导出字段及 Markdown 转义；P2 另覆盖邀请过期/复用、成员移除、备注可见性、并发冲突。
- 真实微信登录、真机 `.md` 分享等真实环境项：环境缺失时只标 `PASS_CODE_ONLY`，不以合成测试替代。

### P1（可延后，摘自 roadmap"后续功能候选"高优先级）
- 低库存阈值提示。
- 临期／过期的微信订阅提醒。
- 批量盘点。
- 完整备份导出。

### P2（候选，中优先级）
- 条码辅助检索。
- 服药计划与确认记录。
- 个人用药历史。
- 自动扣库存（若引入，须先建立明确的确认与撤销机制）。

## 4. 待确认问题（共 4 项，均为 roadmap 真正未定项）

1. **导出是否包含存放位置**：产品边界提到"知道药放在哪里"，但 Markdown 导出条款未明确列出存放位置字段，需确认是否纳入导出内容。
2. **邀请凭据的交付形态**：一次性凭据（口令文本/二维码/链接）的具体输入方式未定，影响小程序邀请入口交互设计。
3. **成员自助退出家庭**：roadmap 只定义了 owner 移除成员；用户想更换家庭时是否提供自助退出入口（而非仅由 owner 移除）未明确。
4. **归档药品是否进入导出**：导出定义为"全量库存"，已归档药品是否排除未明确。

## 5. 边界与红线

- 应用内**不问诊、不推荐用药**，导出不作服药建议；有药不表示适合某人服用。
- **不自动扣减库存**；自动扣库存属后续候选且需确认/撤销机制。
- **无真实密钥**：AppID/AppSecret/第三方密钥不入仓库，仅服务端环境读取；开发默认口令环境仅限本机回环。
- **隐私默认最小化**：个人剂量备注默认仅本人可见；导出默认不含个人剂量；不根据药名或常见剂量生成个人用药信息。
- 真实环境验收项（真实微信登录、真机 `.md` 分享、真实 PostgreSQL、两账号共享实测）在环境缺失时标 `PASS_CODE_ONLY`，不以合成测试或 HTTP 200 推断为真实通过。
- 合成结果不得登记为真实数据库或微信验收；不修改 Docker 引擎配置、代理或系统网络以绕过阻塞。

## 6. P3 / P4 说明（本轮不实现）

P3 为拍照识别与药品资料补齐（识别草稿确认后入库，适配器密钥留在后端）；P4 为上线准备与家庭试用（正式部署、备份与真机双人实测）。两者均在本轮 MVP 验收后另行排期。
