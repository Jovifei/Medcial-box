## 1. 当前最终目标

在不破坏已有家庭数据、登录/权限、库存批次和识别管道的前提下，把微信小程序与 Flutter 统一成易用的家庭药箱：

- 一级入口固定为“药箱 / 用药计划 / 我的”；待处理并入药箱关注区域。
- 首页突出当前家庭、搜索、需关注事项、药品图文卡和一个录入入口。
- 详情页按“身份 → 库存批次 → 照片与资料 → 更多操作”组织。
- 录入页先采集药盒/说明书/扫码，再核对药名、库存和有效期；低频资料折叠。
- 多张照片逐张展示、逐张识别、保留图号和来源；冲突由用户选择。
- 用途/人群可以预勾选，但人工修改和主动清空优先；不把识别结果当作个人用药建议。
- 页面视觉采用暖白、医疗绿、可读字号、稳定图片占位和足够触控区域。
- 保留历史数据和既有路由，收纳功能而不是删除数据或业务能力。

## 3. 当前仍未完全对齐的地方

### P1：录入页仍会把低频资料整体展开

小程序 `medicine-edit.ts` 在说明书识别或候选资料填充后会设置 `optionalExpanded = true`；Flutter `medicine_entry_api_page.dart` 在候选应用、说明书结果等路径会设置 `moreExpanded = true`。这会把品牌、厂家、批准文号、成分、批号/包装换算、说明书摘要等多个低频区一起推到用户面前。

推荐行为：只自动展开“有冲突/必须核对的字段”和核心识别结果；其余资料继续保持折叠，并在折叠标题旁显示“有待核对资料”。这属于页面行为调整，不能删除字段或改变保存契约。

### P1：详情页的说明资料仍有重复展示风险

小程序详情页同时保留 `leafletText` 的摘要行、照片资料区的包装/成分资料和逐项照片信息；Flutter 详情页也保留用途标签和照片资料来源折叠区。当前测试确认主要业务路径可用，但视觉上仍可能让用户连续看到用途、用法用量和来源提示。

推荐行为：详情首层只保留一次短摘要；照片资料区负责“图几、识别状态、原图和来源”；完整原文只在照片资料页阅读。不得删除保存的数据，只减少重复渲染。

### P2：首页筛选仍偏多

状态面板一次仍提供“临期/过期、已过期、库存不足、已用完、数量/日期未知、已开封、已归档、资料完善建议”等多个选项，同时还有用途、人群和排序。功能正确，但不符合“首屏低噪声”的目标。

推荐行为：首层只保留“用途 / 人群 / 状态 / 排序”四个入口；状态面板先放临期、过期、库存不足、待核对，归档和资料完善建议收进“更多状态”。

### P2：我的页面已经分组，但仍然偏长

小程序和 Flutter 都已按家庭、工具、数据、账号/设备、版本分组；设备会话、提醒、备份、导出、最近删除和变更记录仍使页面较长。建议保持分组，优先把低频设备会话和版本帮助维持折叠，不再增加新的中转页。

### P2：视觉规范尚未完成设备级验收

- 页面仍有文本 glyph 作为搜索、箭头和折叠符号（例如 `⌕`、`▾`、`›`、`⌃/⌄`），跨平台一致性不如统一矢量/平台图标。
- 小程序存在 20–22rpx 的辅助文字和标签；代码已有触控尺寸约束，但 320 宽、横屏、系统大字和真实读屏仍未完成设备验收。
- 当前未完成暗色模式、系统动态字体和真实双手机截图验证，因此不能宣称视觉已经完全收口。

## 4. 逻辑是否还有冗余

安全和数据保全逻辑不应因为“看起来复杂”而删除。当前必须保留的复杂度包括：

- 登录/家庭身份代次和迟到请求隔离。
- 照片本地所有权、写入租约、关闭文件描述符和 ready 回执顺序。
- 多图来源、批次来源、stale 回执和旧 API 降级。
- 人工修改/清空优先和候选资料仅作建议。
- 备份范围、照片不在 JSON 中、跨家庭权限和版本冲突。

真正可收口的冗余主要是展示触发：`optionalExpanded` / `moreExpanded` 的自动展开范围、详情摘要重复渲染、首页状态筛选过多。它们应通过 UI 层重排解决，不应改成删除字段、跳过来源提交或绕过冲突确认。
