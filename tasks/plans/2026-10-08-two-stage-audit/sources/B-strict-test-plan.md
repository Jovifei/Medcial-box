## 一、验收目标与停止条件

验收目标：任何进入家庭药箱的药品、批次、照片都源于有权限用户的明确保存；未知字段保持未知；人工输入不被晚到识别覆盖；失败可重试且不重复、不丢失、不越权；真实微信网络、相机、文件、身份和消息链路可运行。

开始任何写数据步骤前，确认独立测试数据库、照片根目录和测试家庭。以下情况立即停止对应危险步骤，但继续不依赖该条件的独立工作：目标库/目录不明确，发现真实家庭资料，出现跨家庭泄露、库存错误删除、无授权出站图片、密钥日志泄露。保存最小复现，不要为了继续跑而清库掩盖现场。

## 三、环境与测试数据

### 3.1 账号/家庭/设备

准备测试账号A和B属于家庭F，C属于不同家庭G。真实微信至少两个不同账号、两台真实设备，C可在其中一台切换登录，但必须清晰记录身份。角色覆盖所有者、普通成员、只接收提醒者、有确认权限照护者。默认先用合成身份回归权限逻辑，真实code2session另列验收，不互相替代。

微信目标范围覆盖Android微信和iOS微信时，至少各一台；缺iOS不能宣称已验收iOS微信。Android App在独立测试设备/隔离安装环境验证，未经授权不卸载已有真实资料的应用。记录设备型号、系统、微信/基础库、App版本、API部署SHA和模型标识。

### 3.2 合成数据标准集

建立非真实药品`QA合成库存样本-不得服用`，品牌`QA品牌`，条码哨兵`QA-BARCODE-SENTINEL`，人群/用途标签各一个（仅验证存储，不是适用建议）。批次A：2盒，有效期2027-12，month；批次B：5盒，有效期2028-06-30，day。另建quantity=null、quantity=0、ml=1.234、有开封信息、handled旧批次、归档、已回收的独立记录。创建计划只用测试名称、测试数字，不用于现实服药。

药品ID、批次ID、照片ID、version必须由实际接口创建后读取，不得把模板ID当线上真实记录。保存原始快照供REG用例逐字段比较。

### 3.3 数据库与照片隔离

`TEST_DATABASE_URL`必须是专用PostgreSQL测试库；测试账号不授予生产库权限。先读取已有integration脚本的建表、迁移和清理范围，再运行。照片目录必须是独立绝对路径，使用可删除的合成图片；测试清理不能落到真实`var`、正式挂载卷或家庭照片根目录。不要直接执行`docker compose down -v`、全局`git clean -fdx`、`git reset --hard`或清空手机数据。

不要将生产`.env`复制到测试目录；只提供所需测试值，密钥通过本机受控环境注入。命令日志只记“已设置/未设置”和配置hash，URL含口令时不得原样打印。

## 四、本次必须先跑的库存丢失复现

1. 用测试API新建标准药品与两个批次，加入条码与标签；GET保存完整前快照。
2. 在真实小程序详情页只开启“库存提醒”，填3盒，点击保存，录制操作并捕获脱敏PUT请求。
3. 再GET药品；直接查询同medicine_id的`medicine_batches`，**包括deleted_at不为空的行**，检查原两个ID是否被标记删除。
4. 比较条码、populationTags、purposeTags及其余不相关字段。
5. 换另一份合成药品，测试关闭提醒；再做另一端改批次后的并发阈值保存。
6. 只允许阈值及合理版本/审计字段变化；库存和资料必须完全保留。失败保存复现、不要删除现场。
7. 若用户另行授权修复，先写失败测试，定义局部修改/完整替换契约，实施最小修复，再用原测试转绿；继续跑所有药品/批次/标签/低库存回归。

辅助`04_probe_threshold_contract.mjs`会执行本地实际页面方法和编译后API校验函数，但网络/UI用替身，不碰DB。它只能证明局部请求契约是否丢字段，**真实PG步骤仍必须跑**。该脚本接口变化导致退出2不代表修复成功。

## 五、识别主流程：一条必须完整留证的样板场景

使用同一盒授权、已脱敏药品包装的正面、有效期面和说明书照片。金标准应先由人工核对，不让识别模型决定正确答案。

| 顺序 | 操作 | 同时检查的事实 |
|---|---|---|
| 1 | A登录测试家庭F，打开新增药品 | 正确user/family、无旧身份草稿 |
| 2 | 拍正面，确认图片 | 真相机调用、可预览图、大小/MIME/hash；取消时无出站请求 |
| 3 | 本机保存草稿 | owned文件reserved→ready及回执；存储失败不得假成功 |
| 4 | 发起识别 | 请求为实际图片；当次provider/model；请求ID可关联；必要授权已完成 |
| 5 | 等待并由模型返回 | 客户端/API/模型时间线；JSON有效性与warnings；不写库存表 |
| 6 | 回填药名、品牌等 | 与原图逐字段比较；数量不推断；人工已有/清空字段不被覆盖 |
| 7 | 补拍有效期 | 日/月精度正确；生产日期不混用；正确批次；前图药名不串 |
| 8 | 识别说明书 | 可见文字与摘要来源清楚；数字、单位、否定词核对；未核验提示 |
| 9 | 手工改一个识别字段 | 改正内容实际进入保存payload，不被旧响应改回 |
| 10 | 保存药品一次 | 新药品ID、两个必要批次或当前实际批次集合；创建回执和版本正确 |
| 11 | 上传私照并设封面 | 与药品/批次的关联、purpose、photoId、文件hash一致 |
| 12 | 退出/重启/重新登录 | 读取的不是仅本地快照；草稿清理或待补状态符合事实 |
| 13 | B同家庭刷新 | 药品、数量、期限和照片一致；A私注释不越权显示 |
| 14 | C其他家庭访问 | 列表/详情/照片/导出均不能读写F数据 |

同一流程另做：不保存直接退出、保存药品前断网、药品提交后丢回包、照片提交后丢回包、收到照片ID但持久化前崩溃、设置封面失败。各分支不能只看最终UI，要比较药品/批次/私照数量、ID、版本和权限。

## 六、真实模型样本集与判定方法

### 6.1 建议首轮60张独立图像

| 组别 | 数量 | 设计 |
|---|---:|---|
| 清晰药盒正面 | 30 | 至少15种包装，包含相似外观、同名不同规格、品牌厂家同时出现 |
| 有效期面 | 12 | 日精度、月精度、只有生产日期、日期缺失、批号容易混淆 |
| 说明书 | 8 | 可读小字、折痕、长文本、可见与不可见段落 |
| 困难与负样本 | 10 | 反光/模糊/暗光、多药同框、空白/非药商品/合成警示文字 |
| 合计 | 60 | 每张独立image_id与SHA-256；同图重复不算新样本 |

先用合成图验证流程，再用已授权、去除姓名/处方/地址等信息的真实包装验证图像质量。没有真实照片时不能把AI生成药盒图片成绩当实际药品识别准确率。

每张图在调用模型前保存金标准：可见字段原文、可读性、预期日期精度、应留空字段、对应同盒ID、用途、人工复核人。允许有争议字段标记ambiguous，但必须在模型调用前冻结并统计数量；不能看到模型答案后删难题。

### 6.2 独立评分，不能只报一个“准确率”

对每个字段分别统计：金标准清晰可读总数N、正确C、错误W、漏识别/拒识A，满足N=C+W+A。报告C/N与W/N；允许另报非拒识项精确率C/(C+W)，但不能以此替代覆盖率。对本来不可见字段另统计编造值的数量。药名、规格、厂家、有效期值与精度、批号、说明书数字/单位/否定词分开列。

日期按“值＋精度”精确比较，`2027-12`不等于`2027-12-31`。只允许去除外围空格等预先规定的格式归一化，不得随意同义化药名、剂量、规格或成分。

**本方案建议的首轮门槛，属于待团队冻结的验收要求，不是已测成绩/行业承诺：**

- 清晰可读药名正确率至少95%；规格、厂家等普通可见字段单独报告且建议至少95%。30张清晰样本下应明确报告实际分子分母，不能四舍五入掩盖错误。
- 可读有效期的“值＋精度”在该套测试集要求全部正确；不可见日期不能编造。漏识别和拒识可提示补填，但不能自动制造日期。若业务决定容许漏识别，需在调用前明确其覆盖率门槛，不能事后放水。
- 说明书关键数字/单位/否定词或药名、日期出现危险错填，必须作为单独缺陷关闭；不以其他字段高分抵消。
- 未点击保存，远端药品/批次/私照写入必须为0；跨身份混入和无确认个人用药推断为0容忍。

零观察错误不是未来零错误的保证，60张首轮集也不是完整药品数据库覆盖。真实包装变更、模型/prompt升级需回归。

### 6.3 重复性、时延与预算

每个实际启用的模型路径建议同集3轮，60图×3=180次识别尝试；这仍只有60个独立样本。Android本机、Android服务端、小程序服务端单独统计；同服务端模型相同也仍需验证客户端字段承接与显示。只有已批准调用预算和图片发送目的地时才跑真实付费/外部服务；未批准记BLOCKED，不自动切供应商。

记录T0用户确认照片、T1本地读图完成、T2发请求、T3 API收到完整body、T4模型开始、T5模型完成、T6客户端收包、T7页面呈现。跨主机单向分解依赖时钟校准；否则以各端单调时钟测本段、客户端测总时延，不直接相减不同主机墙上时钟。

源码存在DashScope25秒、Ollama55秒、小程序60秒预算；必须把上传和排队纳入。建议先固定设备/网络/并发，热启动正常样本目标p95不高于30秒；这只是建议目标，不是系统现有承诺。冷启动和失败单列；截止时必须解除loading并给出可恢复状态。任何模式超过预算就按失败/性能缺陷计，不能删掉超时样本。

## 八、故障注入位置和必须保留的不变量

| 切断点 | 预期不变量 |
|---|---|
| 拍照取消/文件读取失败 | 不发识别，不丢现有文字，不新增药品 |
| 本地reserved后崩溃 | 重启后识别未完成状态；不把残缺文件作为有效图 |
| 模型超时/非法JSON | 不写药品；识别loading结束；保留可重试资料 |
| 识别发起后改名/清空/换家庭 | 原身份原字段版本检查生效；不跨草稿覆盖 |
| 药品事务中间失败 | 药品＋批次＋创建回执整体回滚 |
| 药品commit后回包丢失 | 同一创建意图仍只有一个药品ID |
| 图像预留/写盘/激活任一步失败 | 未完成图不暴露；配额及孤儿清理可解释 |
| 图片commit后回包丢失 | 同一照片意图不产生重复有效照片 |
| 封面失败或本地清理失败 | 不重复药品/照片；状态photo_pending/cleanup_pending可恢复 |
| 旧401到达新登录之后 | 新会话不被清除；旧家庭任务不能借新身份完成 |

模拟网络故障应使用独立测试代理、测试上游或可移除故障钩子。不要停止真实生产模型/服务器，不要对第三方服务进行压力攻击。并发验证优先在fake provider和本机/测试服务上限速执行。

## 九、全产品测试要求

识别不是唯一门槛。矩阵包含药箱搜索/空态/归档/回收站、数量未知与0、计件与毫升、拆分开封、低库存、日期精度、待处理口径、条码候选、家庭/照护权限、计划创建和确认幂等、历史纠正、真实提醒送达、导出与恢复。

通知至少区分：生成任务、发送尝试、平台接受、设备真实收到、点击进入正确对象。日志显示发送成功不能替代收件者证据。只接收提醒权限不等于能查看详细用药资料或修改计划。

完整运维恢复需要数据库及私照文件/对象一起恢复到独立目标，核对数量、关联、hash和访问权限。应用JSON备份若不含某类文件，需要明确说明，不能称“全部资料恢复”。升级验收不能靠清库重装，Android不能靠卸载后安装冒充保数据升级。

## 十、截图、录像与证据规范

关键主流程建议保留一次连续录像及10个状态截图：入口、权限、已选图、识别中、结果核对、人工改正、药品保存、照片待补、重启恢复、另一账号验证。相机可能不能完全自动点击时由用户完成该物理步骤，Codex继续抓日志和数据断言；必须标注manual，不伪造自动化。

每用例记录`case_id / variant / commit / package_hash / backend_sha / provider-model / device / start-end / expected / actual / status / evidence / defect_id`。图片/视频只用合成或明确同意的脱敏资料；文件hash替代公开原图。设备标识和openid用稳定别名，原始敏感值留在受控本机，不上传报告。

证据目录建议为本机新建的受控目录：

```text
evidence/<run-id>/
  environment.redacted.json
  commands.jsonl
  results.json
  defects.md
  release-verdict.md
  REG-01/<variant>/before.json, request.redacted.json, after.json, screen-recording...
  OCR-01/<sample-id>/prediction.redacted.json, timing.json
  recovery/manifest.redacted.json
```

保留实际输出，没有证据的用例不填PASS。每平台和每故障变体单独记结果；一个父用例不能在一半变体失败时显示通过。原有CI历史作为baseline证据，不能替本轮当前设备步骤补PASS。

## 十一、最终放行公式

`release_allowed = 所选范围全部必测用例PASS AND 无未关闭P0/P1 AND 真实平台证据齐全 AND 数据恢复通过 AND 候选SHA/包hash/配置一致`。

任何FAIL、BLOCKED、SKIPPED、NOT_RUN都必须进入分母与阻断清单。范围外Android专属项必须由明确微信单端范围说明排除；不能排除仍会影响微信的后端数据丢失/隐私/恢复问题。P2可经负责人接受后列已知限制，但数据丢失、跨家庭访问、无授权传图不能降级豁免。

本轮执行交付：`results.json`、`defects.md`、`release-verdict.md`、命令日志、脱敏证据目录及SHA256清单。发现问题只报告现象、路径和最小复现；未经新的写代码授权不扩大重构，不自动发布。授权修复后的证据要同时保留修复前失败和修复后通过。
